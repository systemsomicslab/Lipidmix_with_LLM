# 解釈品質評価ハーネス 設計（ステップ4＋5）

- 日付: 2026-07-07
- 対象: ローカルLLM移行のステップ4（解釈品質評価）＋ステップ5（ハイブリッド分界点＝今回はエスカレーション集合の特定に読み替え）
- 前提: ルーティングは解決済み（`phase_router` / `agent_core` / `phase_router_eval.py`、qwen3:14b think OFF で subset 満点）。本 spec はその上に載る新規テーマ。

## 1. 目的と非目的

### 目的
ローカル3モデルの**科学的解釈の品質**を、ルーティングと切り離して単離測定する。得たいアウトプットは2つ:

1. **モデル選定の根拠**: 3モデルのうちどれが「解釈担当」に足るか（think ON の6倍コストが解釈品質で見合うか、7B が退避先として実用か）。
2. **エスカレーション集合**: 最良のローカルモデルでも力尽きるフェーズ／クエリ種別（ハルシネーションや品質破綻が出る所）を洗い出す。これが将来クラウド腕を足したときの「投げ先候補」になる。

### 非目的
- ツールルーティングの再評価（解決済み。`phase_router_eval.py` が担当）。
- クラウドモデル（gpt-4o-mini / フロンティア）の測定。今回クラウドは一切使わない（移行の動機＝トークン課金削減）。
- クラウド分界点の**閾値確定**。クラウド腕が無いため今回は測れない。ステップ5は「エスカレーション集合の文書化」までとし、実閾値は後日 `chat_fn` にクラウド腕を差し込んだ時点に持ち越す。

## 3. 評価対象と測定法

### A案（主軸）: 解釈の単離
1. 実データで対象ツールを一度走らせ、**戻り値 JSON を凍結**（決定的なので誰が走らせても同じ）。
2. 凍結した tool 出力を含む固定会話 `[system, user(query), assistant(tool_calls), tool(結果)]` を構築。
3. 同一の凍結入力を3モデルに渡し、**最終の解釈テキストだけ**を生成させる（追加のツール呼び出しはさせない＝解釈のみを単離）。
4. `chat_fn` の差し替えでモデルを切り替える（`Agent` の DI 構造をそのまま利用）。

利点: ルーティング差・ツール実行のばらつきを排除し、純粋な解釈能力だけを測る。再現性が高い。

### B案（補助・2〜3ケース）: フル一気通貫
- フル `run_turn`（route→ツール実行→解釈）を各モデルで走らせ、最終応答を確認。
- 目的は採点ではなく**裏取り**: A の凍結入力が実運用（実際に route が選ぶツール・実際の戻り値）と乖離していないかの確認。

## 4. 採点

### 審判と校正（二層）
- **①バックボーン = LLM-as-judge**: この Claude Code セッション（私）が審判。ハーネスはモデル名を伏せた**盲検比較シート**を生成し、私がそれを読んで採点する。追加API課金ゼロ。Qwen と別系統の frontier 審判。
- **②校正 = 人手**: ユーザーが十数件を抜き取りで採点し、①の判定が人手と一致するかを確認する。リピドミクスの専門判断の接地点。

### 比較方式
- **盲検ペア比較**: どのモデルの出力かを伏せ、候補間の総当たり `1v2 / 1v3 / 2v3` ＝ 1ケース3ペア。順序バイアスを避けるため A/B の提示順はケースごとにランダム化（またはシート上で明示的に入れ替え）。
- 各ペアで「総合の勝敗（A勝ち / B勝ち / 引き分け）」＋「5軸それぞれの勝敗」を記録。

### 5軸ルーブリック（①を最上位ゲート＝辞書式順序）
| 軸 | 定義 | 扱い |
|---|---|---|
| ① ハルシネーション（接地性） | tool 出力に無い数値・主張を捏造していないか。根拠必須 | 最上位ゲート。致命的違反があれば他がどれだけ良くても即負け |
| ② 科学的正確性 | 解釈がリピドミクス的に妥当か（群分離の方向・脂質クラスの意味づけ等） | 本体（高） |
| ③ 完全性 | tool 出力の重要所見を取りこぼしていないか（主要な差次・QC異常など） | 本体（中） |
| ④ 実用性／次の一手 | 次に呼ぶべき解析や注意点を適切に示唆できているか | 付加価値（中） |
| ⑤ 言語・形式の安定性 | 日本語で簡潔か、多言語ドリフト・冗長 narration がないか | ゲート（低）。破綻は減点。14B が full モードで中国語/タイ語ドリフトした実績への対策 |

### 集計
- モデルごとの**ペア勝率**（総合／軸別）。
- **フェーズ×軸のヒートマップ**: どのフェーズ・どの軸で最良ローカルが負けるかを可視化 → ステップ5のエスカレーション集合の根拠。

## 5. データセット

- **源**: liver の `C:\Users\yuu18\datasets\2_lipidome_lcms\NEG` と `...\POS`（`LIPIDMIX_DATA_DIR` で切替）。
- **規模**: 5フェーズ × 2ケース = **10ケース**。各フェーズ **NEG 1件＋POS 1件**（イオン化モード差への頑健性も同時に観測）。

| フェーズ | 凍結する tool 出力の例 | 解釈が問われる点 |
|---|---|---|
| FIGURES / PCA | PCA座標・寄与率・群ラベル | 群分離の方向と生物学的意味づけ。幻覚の温床 |
| 差次的解析 | fold change・p値・上位脂質 | 有意性の読み・多重比較の注意 |
| 前処理 / QC | 正規化前後・QC指標 | 異常検出と対処提案 |
| 同定 / 確信度 | 脂質同定・スコア | 確信度の適切な留保（過剰主張の危険） |
| 文献 / 知識 | paper_search 結果・GAP 小問 | 出典の接地・カバレッジ判断 |

- 現データで叩けないフェーズがあれば、実装時にそのフェーズのケースを差し替える（データ源の実内容に依存するため、ケース確定は凍結ステップで最終化）。

## 6. 成果物（コード）

既存 `phase_router_eval.py` の隣に置く手動スクリプト群（Ollama 起動が前提）を想定:

1. **凍結ハーネス**: 10ケース分、対象ツールを `execute_tool` で一度走らせ、戻り値 JSON を保存。ケース定義（クエリ・フェーズ・ツール・引数・データ源）はデータとして持つ。
2. **解釈生成ハーネス**: 凍結入力 × 3モデル（think OFF / ON / 7B）で解釈テキストを生成し保存。`chat_fn` 差し替えでモデル切替。追加ツール呼び出しはさせない。
3. **盲検シート生成**: モデル名を伏せ、ケースごとに候補ペアを提示するシート（私が読んで採点する形式）。採点結果を受けて集計（ペア勝率・フェーズ×軸ヒートマップ）を出す。

## 7. ステップ5（読み替え）

クラウド腕が無いため閾値は測らず、**「フェーズ×軸で最良ローカル（想定 14B）がハルシネーション／品質破綻を起こす集合」を文書化**する。`chat_fn` が DI なので、後日クラウド腕を差し込めば実閾値の測定に移行できる。今回の成果物はその測定台になる。

## 8. 未解決・実装時に確定する事項

- 現データ（NEG/POS）で「文献/知識」フェーズと「同定/確信度」フェーズが実際に動くか。動かなければケース差し替え。

- 盲検シートのフォーマット詳細（採点の一貫性を保つ最小構造）。
